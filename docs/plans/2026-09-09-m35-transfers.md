# M3.5 (second half) — A transfer is not a sale · Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement
> this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A spot ↔ futures transfer is recorded as what it is — money moving between two
wallets of one account — and never as a disposal followed by an acquisition.

**Architecture:** The universal-transfer endpoint reports **one row per transfer**, with the
direction encoded in its `type` (F10). So the intra-venue case needs no matching heuristic
at all: the row is the whole transfer. What it needs is a ledger event that names both
endpoints, and a balance fold that knows a move between two wallets of the same integration
is not a movement of the account's money.

**Tech Stack:** Go 1.26 · Postgres 18 · goose · sqlc · the existing normalizer, backfill and
projection machinery.

**Spec:** `docs/DECISIONS.md` K12 K19 K22 K44, `docs/ARCHITECTURE.md` §3 §8,
`docs/PROJECT.md` §8 (M3.5 row), `CLAUDE.md` L2 L3 L5 L7 L9

## Context

M3.5's first half shipped with M3: the negative-balance check (K44), the projection-lag and
unknown-symbol reasons, and the asset fold that makes them possible. The second half is the
one the milestone is named for, and it has been last on purpose — nothing produced a
`TRANSFER` event, because V1 ingests spot and Binance reports an intra-venue move through a
wallet endpoint rather than through the spot trade stream.

`internal/balance` already reserved the shape: a transfer's quantity is **signed**, positive
in and negative out, and a test enforces it. This plan is what fills that branch — and it
changes the answer, for a reason the verification produced rather than confirmed.

### The four decisions taken before writing this plan

| Question | Decision |
|---|---|
| Match two halves, or record one row? | **One row.** F10: the venue reports one record per transfer with the direction in `type`. The K12 heuristic (amount within fee tolerance, time window, txid) is what you need when a venue reports the two halves separately — which is **cross-venue**, and stays in M8. |
| What does an internal transfer do to the balance? | **Nothing.** `asset_balances` is keyed per integration, not per wallet, and moving USDT from the spot wallet to the futures wallet of one account does not change what that account holds. It folds to zero deltas, and the event stays in the ledger for lineage. |
| Then why store the endpoints? | Because M5 needs them. Margin buffer is a per-wallet question, and `transfer_from` / `transfer_to` are exactly the columns a wallet-aware balance folds over. Storing them now costs two nullable columns; recovering them later costs a replay. |
| Which of the 32 transfer types are walked? | The eight that move value between wallets V1 knows about: `MAIN_UMFUTURE`, `UMFUTURE_MAIN`, `MAIN_CMFUTURE`, `CMFUTURE_MAIN`, `MAIN_MARGIN`, `MARGIN_MAIN`, `MAIN_FUNDING`, `FUNDING_MAIN`. Options and portfolio-margin wallets are not ingested at all, so walking them would record halves of movements whose other side does not exist here. |

### What this plan does not do

`transfer_links`, `GET /transfers?unmatched=true` and `POST /transfers/{out}/link/{in}`
(`ARCHITECTURE.md` §5) stay unwritten. They are the cross-venue machinery, and building a
matching queue for a case that produces one unambiguous row per transfer would be building a
UI for a problem this milestone removes. M8 is where they earn their place.

## Global Constraints

Every task's requirements implicitly include this section.

- **L1** — money is `NUMERIC(38,18)` / `decimal.Decimal` / a JSON **string**.
- **L2** — the ledger is append-only. A corrected transfer is a new event.
- **L3** — `asset_balances` must survive a drop and rebuild byte-identically. Any change to
  the fold gets a rebuild-equality test.
- **L5** — identity is `(integration_id, venue_event_id)` and excludes `source`.
- **L7** — canonical order is `(event_time, venue_sequence, venue_event_id)`.
- **L9** — a fee belongs to the event that caused it. A transfer fee is the transfer's.
- **L13** — no credential in a log, an error, or a fixture.
- Fixtures before network. Never iterate against the live API.

## Task 3: An internal transfer is not a movement

This is the task the milestone exists for, and it is pure: no database, no clock (L4).

- [x] **Step 1: Failing test — a transfer between two wallets of one integration produces no
  deltas.** The account holds exactly what it held; the event is history, not arithmetic.
- [x] **Step 2: Failing test — a transfer with `external` on one side still moves the
  balance**, signed by which side is external. This is the branch M8 turns on, and writing it
  now is what keeps the internal case from being special-cased into the only case.
- [x] **Step 3: Failing test — the seller's fallacy.** A transfer out followed by fills that
  spend the same asset must leave the balance the fills alone would, and the realized PnL of
  the position untouched. This is "a transfer is not a sale" stated as arithmetic.
- [x] **Step 4: Implement, then rebuild-equality (L3).** Drop `asset_balances`, fold again,
  compare byte for byte with a transfer in the stream.
